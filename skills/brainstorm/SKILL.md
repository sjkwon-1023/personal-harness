# Brainstorm

구현 전에 사용자의 의도를 합의한다. 의도와 다른 구현과 필요 이상의 고도화를 막는 것이 목적이다.
사용자가 합의 요약을 확인하기 전에는 코드·스캐폴딩·설정을 만들지 않는다.

## 반드시 합의할 것

- 목적과 사용자: 무엇을 누구를 위해 하는가, 무엇이 되면 성공인가
- 완성도 수준: PoC / MVP / 운영. 수준에 맞지 않는 추상화·확장성·테스트는 넣지 않는다.
- 범위와 비범위: 이번에 하지 않을 것을 명시한다.
- 완료 기준: 무엇을 보면 끝났다고 판단하는가
- 제약: 기존 코드·계약·기술 선택, 바꾸면 안 되는 것
- 필요성: 전역 지침의 확인 순서로 꼭 필요한지, 기존 코드·표준 라이브러리·플랫폼 기능으로 되는지 따진다.

## 조사

사실은 사용자에게 묻지 않고 직접 찾는다. 사용자에게는 결정만 묻는다.

- 코드·문서·git 기록으로 현재 구조, 재사용할 코드, 영향받는 계약을 확인한다. 넓은 코드 탐색은 repo-scout 서브에이전트에 맡길 수 있다.
- 구현 가능성이 불확실하면 라이브러리·플랫폼·외부 API의 공식 문서를 찾아본다. 필요하면 프로젝트를 바꾸지 않는 짧은 실험(읽기 전용 명령, 임시 디렉터리)으로 확인한다.
- 방향이 갈리면 2~3개 방안을 장단점·비용·위험과 함께 비교하고 추천안을 낸다.
- 조사 결과는 출처(파일 경로, 문서 URL)와 함께 짧게 제시하고 확인한 사실과 추정을 구분한다.
- 조사 중인 사실에 걸린 질문만 미루고, 나머지 질문은 먼저 묻는다.
- 사용자가 조사 모델을 지정하면(예: `codex:top`, `claude:top`) 그 조사는 `~/.config/coding-harness/pane/PANE.md` 절차로
  `--role research`에 맡긴다. 브리프에는 조사 질문, 지금까지 합의한 목적·완성도 수준·범위, 관련 코드 경로를 넣는다.
  여러 모델에 맡기면 같은 브리프를 주고 결과를 비교해 제시한다. 회신을 기다리는 동안 조사와 무관한 질문을 진행한다.

## 진행

질문을 결정 트리로 다룬다. 한 라운드에는 전제가 이미 정해진 질문만 묶어 번호를 붙이고, 각 질문에 근거와 추천 답을 단다.
다른 질문의 답에 따라 달라지는 질문은 다음 라운드로 미룬다. 답을 받으면 합의된 결정을 한 줄로 되짚고 다음 라운드를 연다.

```text
**Q1. <질문 제목>** <질문 내용과 선택지>
→ 추천: <추천 답과 근거>
```

## 끝내기

열린 질문이 없으면 합의 요약을 내고 사용자의 확인을 받는다.

- 목표와 성공 기준, 완성도 수준, 범위, 비범위, 완료 기준, 제약
- 결정 목록과 각 근거, 남은 위험과 확인 필요 사항

확인되면 전역 지침에 따라 "dispatch-plan으로 구현할까요?"라고 묻고, 중요한 기능이면 `docs/plans/<feature>-plan.md` 기록을 제안한다.
새 세션으로 넘길 때는 session-handoff를 쓴다.
